Deployment Guide & Runbook — Go stack, single-host

First deployment on a new Linux host (steps 1–10), then the on-call runbook: upgrades, rollback, troubleshooting and commands.

What You'll Build

Mobile app ─HTTPS─► nginx :443 ─┬─ /collector-go/ ─► Collector-Go     127.0.0.1:8001
Dashboard  ─HTTPS─►             ├─ /processor-go/ ─► Processor-Go     127.0.0.1:8002
                                └─ /api/          ─► RUM Analytics Go 127.0.0.1:8003

Collector-Go ─► Kafka (telemetry-upsert) ─► Processor-Go ─► PostgreSQL (external)
RUM Analytics Go ◄── PostgreSQL + Redis   ·   API keys: Analytics ─► rum-api-keys ─► Collector
  • Collector-Go: ingest API, validates API keys
  • Processor-Go: Kafka consumer, writes rum_* tables
  • RUM Analytics Go: dashboard API
  • Kafka + Zookeeper: broker (not published)
  • Redis: cache + rate limits (not published, password required)
  • Kafka UI: loopback only, login, SSH tunnel

PostgreSQL is never bundled. Every service port binds 127.0.0.1; only nginx faces the network.

Prerequisites Check

Confirm the host and the inputs you need before touching the server.

Host

  • Linux: Ubuntu/Debian, RHEL/Rocky/Alma/CentOS/Fedora, or SLES/openSUSE (the setup script detects which)
  • 4 GB RAM and 2 CPU cores recommended (2 GB minimum)
  • Disk under /var (Docker volumes) for the Kafka disk budget (default 120 GB) plus ~10 GB for images
  • sudo access; outbound internet to Docker Hub and ghcr.io for image pulls
  • Inbound: 80 and 443 (plus SSH) only. Nothing else needs to be opened.

Inputs to collect

  • Existing PostgreSQL edge_db, reachable from inside containers (a real host/IP, never localhost). The DB role must own the public.rum_* tables and analytics.v_mobile_rum_rca_evidence.
  • The exact EDGE_JWT_SECRET used by edge_platform
  • Dashboard and app origins for CORS
  • Domain name pointing at the server, and its TLS files fullchain.pem + privkey.pem
⛔

Replacing the Python stack?

Both stacks use the same container names and ports and cannot run together. Stop the Python stack first with make down in its deployments/single-host directory. Never make clean or docker compose down -v: the Kafka volume holds queued messages and offsets the Go stack takes over.

  • Check the distro: cat /etc/os-release (or bash getstarted.sh --detect-only)
  • Ports already in use: sudo ss -tlnp | grep -E ':(80|443|8001|8002|8003|8080) '
  • Python stack still up: docker ps --format '{{.Names}}' | grep telemetry-

    • Baseline the Database

    Once per database. make deploy refuses to run without it.

    make db-baseline

    The Go services need a newer schema than the v012 edge_db; Processor-Go's own migrations fail on a raw v012 database. The script checks for duplicate rum_apps.package_name and rum_users.user_id rows, asks for confirmation, then applies shared/sql/go_baseline.sql in one transaction. It drops and recreates analytics.v_mobile_rum_rca_evidence. Re-running is a no-op.

    ⚠

    The rum_* tables are shared with the analytics team. Tell the DB owner before running it.

    • Deploy

    Start the stack.

    make deploy
    1. Runs config-check
    2. Aborts if the DB baseline is missing
    3. Creates /opt/edge-telemetry (asks for sudo)
    4. docker compose up -d: kafka-init creates the topics first, then the services start
    5. Waits 60 s, health-checks, restarts the processor once if unhealthy
    ℹ

    First start runs the processor's and analytics' DB migrations, which can take several minutes. The collector answers 503 until it has loaded the API keys from rum-api-keys. Re-check with make health.

  • Which containers are up: make status; logs: make logs-processor (or collector, rum-analytics, redis, kafka)
  • Processor restart loop with dirty in logs: Runbook → dirty migration
  • permission denied ... docker.sock: run newgrp docker or log in again

    • Configure nginx & TLS

    Services listen on 127.0.0.1 only; nginx terminates TLS and proxies.

    1. Upload the certificate files (from your workstation)

    2. Install them (on the server)

    3. Write the site config

    sudo nano /etc/nginx/conf.d/edgetelemetry.conf # paste the config below

    conf.d/ works on every distro. On Debian/Ubuntu also remove the default site: sudo rm -f /etc/nginx/sites-enabled/default. Kafka UI is deliberately not proxied: reach it over an SSH tunnel.

    4. RHEL family only: let nginx reach the upstreams

    sudo setsebool -P httpd_can_network_connect 1

    5. Validate and reload

    sudo nginx -t && sudo systemctl reload nginx
    🔒

    • The certificate CN/SAN must match the domain
    • Ports 80 and 443 open (the setup script did this)
  • nginx -t fails: check cert paths and permissions, then the config syntax
  • 502 after reload: Runbook → nginx returns 502
  • Editing an existing host: vhosts in sites-enabled/ are often symlinks; find the live file with sudo nginx -T

    Processor will not start: dirty migration

    Processor-Go refuses to start when schema_migrations.dirty = true. Version N dirty means migration N failed and was rolled back in full.

    1. Find and fix the cause: make logs-processor (on a v012 DB, usually make db-baseline)
    2. Clear the flag (sets version N-1, not dirty, after confirmation):
    make db-force docker compose --env-file configs/single-host.env restart telemetry-processor make health

    Never run db-force before fixing the cause: the migration fails again and re-sets the flag.

    DB baseline not applied, or pre-flight fails
    • Not applied: make db-baseline, then make deploy.
    • Duplicates listed: the baseline adds unique indexes on rum_apps(package_name) and rum_users(user_id). Merge each duplicate (repoint child rows to one id, delete the rest) with the DB owner, then re-run.
    • Permission errors: the DATABASE_URL role must own public.rum_* and analytics.v_mobile_rum_rca_evidence.
    nginx returns 502
    1. Is the upstream up? If not, fix the container, not nginx:
    curl -fsS http://127.0.0.1:8001/ready curl -fsS http://127.0.0.1:8002/health curl -fsS http://127.0.0.1:8003/api/v1/health
    1. Editing the live file? sudo nginx -T | grep -n proxy_pass (vhosts in sites-enabled/ are often symlinks: readlink -f)
    2. Ports match: /collector-go/ → 8001/, /processor-go/ → 8002/, /api/ → 8003 (no trailing slash)
    3. RHEL family: sudo setsebool -P httpd_can_network_connect 1 (error log shows Permission denied on connect)
    4. sudo nginx -t && sudo systemctl reload nginx, wait a few seconds, retest

    During make update a 502 on /collector-go/ is expected: the collector is stopped and SDKs queue offline.

    Dashboard returns 401
    1. EDGE_JWT_SECRET must equal edge_platform's exactly (no trailing whitespace, no quotes)
    2. EDGE_JWT_ISSUER and EDGE_JWT_AUDIENCE must be unset
    3. Recreate the container (a restart does not reload env files):
    docker compose --env-file configs/single-host.env up -d telemetry-rum-analytics
    Collector /ready stays 503

    The collector holds API keys in memory, read from the compacted rum-api-keys topic that RUM Analytics produces. Until it has caught up, /ready and ingest answer 503 with Retry-After: 5.

    • Analytics healthy? make logs-rum-analytics — it publishes keys on start
    • Topic exists? Kafka UI, or re-run make kafka-init
    • Collector errors: make logs-collector

    A revoked key gets 401 from the collector within ~10 s, no restart needed.

    Events accepted but not stored / lag alert
    1. make logs-collector: publishing without Kafka errors?
    2. make logs-processor: DB errors (missing columns = schema drift, connection refused)?
    3. make kafka-lag: per-partition lag of the processor group
    4. Poisoned messages: SELECT count(*) FROM processor_dead_letter_events;

    Lag alert. kafka-lag-watch checks the lag every 5 min and logs WARN kafka_lag_high lag=<n> while it exceeds LAG_ALERT_MESSAGES (default 1,000,000 ≈ 48 min of backlog). No notifier: grep for it. kafka_lag_check_failed means the check itself failed (Kafka down); it recovers on its own.

    docker compose --env-file configs/single-host.env logs kafka-lag-watch | grep kafka_lag_high

    Keep LAG_ALERT_MESSAGES below retention.bytes ÷ average message size per partition, or data ages out before anyone is warned.

    Upgrade

    Images are pinned by digest, so an upgrade is always a new deployment package. Download the new zip, copy it to /opt/edgetelemetry, then:

    cd /opt/edgetelemetry rm -rf edge_telemetry_deployment_go.prev mv edge_telemetry_deployment_go edge_telemetry_deployment_go.prev unzip -q edge_telemetry_deployment_go.zip cp -p edge_telemetry_deployment_go.prev/deployments/single-host/configs/*.env \ edge_telemetry_deployment_go/deployments/single-host/configs/ cd edge_telemetry_deployment_go/deployments/single-host make config-check && make update

    make update is stop-the-world: ingest is down from step 2 to 6 (nginx 502, SDKs queue offline and retry).

    1. config-check, pull the pinned images (before anything stops)
    2. Stop the collector: no new messages reach Kafka
    3. Drain: wait for the processor's lag to reach 0 (gives up after DRAIN_TIMEOUT_SECONDS, default 1800, leaving the collector stopped)
    4. Stop processor and analytics; save offsets to backups/offsets-<ts>-before.txt
    5. kafka-init: creates/grows topics, reapplies config (first upgrade grows telemetry-upsert 1 → 12 partitions)
    6. Start analytics (migrations), processor (migrations), collector, each waiting for healthy; save offsets-<ts>-after.txt

    Partition 0's committed offset in the after file must equal the before file. Running make update with nothing to upgrade is safe.

    ⚠

    If the drain times out: fix the processor and run make update again, or give up with a rollback. Plain make deploy would start the new images without the drain ordering.

    Analytics and processor migrations can take minutes on a large DB; the healthchecks allow up to 15 min.

    Rollback

    Images only. Once telemetry-upsert has 12 partitions and new migrations have run, there is no topic or schema rollback.

    cd /opt/edgetelemetry mv edge_telemetry_deployment_go edge_telemetry_deployment_go.bad mv edge_telemetry_deployment_go.prev edge_telemetry_deployment_go cd edge_telemetry_deployment_go/deployments/single-host make update

    Rolling back the processor or analytics does not undo migrations they already applied. Confirm the older image works with the newer schema first.

    Acceptance run
    ⛔

    Writes Apps, API keys and telemetry into this install's DB and Kafka. Never run it on a client install without the operator's consent. Every script refuses unless ACCEPTANCE_OK=yes.

    Needs docker, curl, jq, openssl on the host, the stack healthy, a core.tenants id and an active core.users id of that tenant.

    export ACCEPTANCE_OK=yes ACCEPTANCE_TENANT_ID=<tenant uuid> ACCEPTANCE_USER_ID=<user uuid> make acceptance # X1-X5 + XV, one PASS/FAIL line each, exit 1 on any FAIL make acceptance-clean # RUN_ID=<id> for one run, RUN_ID=all for every run

    X14.0 batch with an App-bound key: headers, session app/environment, rum_app_versions row
    XVAnalytics ?version= and per-version experience return X1's session
    X2Legacy batch + legacy key lands on the matching App; unmatched dead-letters and replays once the App exists
    X3Revoked key gets 401 within 10 s, no restart
    X4Re-consumed messages and double dead-letter replays add no rows
    X5One device's batches share a partition in order; newest event time wins

    Security model
    • Network: every host port binds 127.0.0.1; public traffic enters only through nginx. Firewall opens 80/443 only.
    • Containers: all read_only with no-new-privileges; first-party images run as 65534:65534.
    • Images: first-party pinned by digest, third-party by exact tag.
    • Redis: requirepass mandatory; compose aborts without it.
    • Kafka UI: kafbat, read-only, login form, loopback only, SSH tunnel. Never proxy it publicly.
    • Secrets: env files are chmod 600 and never committed or emailed.
